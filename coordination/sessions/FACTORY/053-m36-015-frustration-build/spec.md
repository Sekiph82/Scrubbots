# Frustration Risk inputs build (HUMAN_BR + Session Load budget)

> Feature: SB-M36-015 - Build the Frustration Risk inputs: HUMAN_BR simulated-human policy population (fixed offline profiles NOVICE/CASUAL/SKILLED, PRIOR_UNCALIBRATED, deterministic seeds; with error knobs 0 it must reproduce the existing ACCESS policy exactly), per-slot Session Load budget, new data/config/frustration_analysis_v1.json, scripts/difficulty/frustration_analyzer_v1.gd, opt-in difficulty_playtest.gd --frustration. F labelled PROVISIONAL_SIMULATED_HUMAN; F null if any input missing; existing configs byte-identical (CLAUDE.md 11.3); profiles never applied per player (no hidden DDA, 11.5). Acceptance tests stay fast; the full shipped-level run is optional evidence, not a gate.

## Context
Design source (owner pre-approved 2026-10-26, read it fully, sections 4 and 5 are normative): `docs/DIFFICULTY_FRUSTRATION_RISK_PROPOSAL_V1.md`. Where this spec and the proposal differ, this spec wins (runtime handling only).

Existing code to reuse, not rebuild:
- `scripts/difficulty/level_difficulty_analyzer_v2.gd` (`LevelDifficultyAnalyzerV2`): `run_policy(level, engine, policy, fixed)` replays a policy through the real `ProofKernel`; it calls the static `choose(policy, st, last, ncols)` on the decision state `st` built by `_v1._decision_state` (`st["fronts"]`: each front has `column`, `color`, `robots`, `raw`, `reachable`, `productive`). ACCESS key is `[min(reach,robots)/robots, reach]`, ties to lowest column (`ACCESS_HI` differs only in tie handling). `MAX_DECISIONS = 2000`. `frustration()` currently returns `scalar: null`, `PROVISIONAL_STAGE_A` and must stay as is.
- `data/config/difficulty_score_model_v2.json` `frustrationRisk` weights 0.35/0.30/0.20/0.15 (read only) and `sessionLoad`.
- `tools/difficulty_playtest.gd` (args via `OS.get_cmdline_user_args()`, existing flags `--model`, `--progression`, `--committed-measure`).
- Corpus fixtures `tests/fixtures/difficulty_calibration/*.level.json` + `*.supply.json` (see how `tests/m53_c002_difficulty_calibration.gd` / `tests/m36_difficulty_v2.gd` load level and build the engine).
- Suite style: copy the PASS/FAIL print convention of `tests/m36_recovery_component_checks.gd`.

## Requirements
1. New `data/config/frustration_analysis_v1.json`, schema `scrubbots-frustration-analysis/v1`, containing: `version`; `status` labels (`PROVISIONAL_SIMULATED_HUMAN`, profiles `PRIOR_UNCALIBRATED`); the three profiles with weight/tau/epsilon/mu/t0/t1 exactly as proposal 4.2 (NOVICE 0.30/0.30/0.10/0.40/1.5/0.8, CASUAL 0.50/0.15/0.05/0.20/1.0/0.6, SKILLED 0.20/0.05/0.01/0.05/0.6/0.4); `runsPerProfile` 32; seed formula string; thresholds 0.70 (late failure, strictly greater) and 0.90 (near miss, >=); `decisionBound` 2000; Hearts max 5; bot speed 6 cells/s; per-slot Session Load budget 22/26/36/40/48 mapped to slots (4,6,9 -> 22; 1,2,7 -> 26; 3,8 -> 36; 5 -> 40; 10 -> 48) labelled `PROXY`; overrun rule `clamp((SL-budget)/budget,0,1)`; a note that profiles are an offline population, never assigned per player.
2. New `scripts/difficulty/frustration_analyzer_v1.gd` (offline QA only):
   - HUMAN_BR chooser per proposal 4.1: perception (prob `mu` uses `raw` instead of `reachable`), utility `min(perceived,robots)/robots`, slip (prob `epsilon` uniform legal front), else softmax over `u/tau`, Hick-Hyman latency `t0 + t1*log2(1+legalFronts)` (diagnostic only). Pool = productive fronts, falling back to all fronts when none, same as `choose`.
   - Degenerate setting (tau -> 0 / argmax, epsilon 0, mu 0) must choose exactly what ACCESS chooses (ACCESS tie-break by `reachable`, then lowest column).
   - One `RandomNumberGenerator` per attempt seeded `hash("%s|%s|%d|%s" % [levelId, profile, runIndex, configVersion])`, draws in fixed order (per front: perception, then slip, then softmax).
   - Reuse `run_policy` through a minimal optional hook: add an optional trailing `chooser: Callable = Callable()` parameter to `LevelDifficultyAnalyzerV2.run_policy` (when valid, it replaces the `choose(...)` call). Default behaviour and all existing outputs must be unchanged. No copied kernel loop.
   - `runsPerProfile` and a profile subset must be overridable by arguments (for fast tests and `--runs N`); the config default stays 32.
   - Outputs per proposal 4.5, per profile and population-weighted: `clearRate` (WON/(WON+LOST), INCONCLUSIVE = decision-bound runs excluded and counted, Wilson 95% interval), `retryRisk`, `lateFailure` (+ LOST count, 0 when none), `nearMiss`, `deadPlacementsPerAttempt`, `noTargetWaitFraction`, `heartsPerClear`, `expectedAttemptsPerClear`, `pOutOfHeartsBeforeClear`, `attemptSecondsProxy` (PROXY), `sessionOverrun`, `choiceOpacity` (reuse v2's `0.5*B + 0.5*nonProductiveLegalFraction`), `F`.
   - `F = 100*(wRetry*retryRisk + wOverrun*sessionOverrun + wLate*lateFailure + wOpacity*choiceOpacity)` with weights read from `difficulty_score_model_v2.json`; status `PROVISIONAL_SIMULATED_HUMAN`; F is `null` (with the missing input named) if any of the four inputs is missing/non-finite. Result carries config version, seeds, analyzer version.
   - Output serialization deterministic (sorted keys / fixed order) so the same run is byte-identical JSON.
3. `tools/difficulty_playtest.gd`: add opt-in `--frustration` and `--runs N`. Without `--frustration` every existing output file and stdout is byte-for-byte unchanged. With it, the tool additionally writes a frustration JSON + markdown table (per-level F, the four inputs, diagnostics, wall time) beside the existing playtest outputs. `--runs N` overrides `runsPerProfile`. Document usage in the file header comment.
4. Byte-identical (sha256 equal to `main`): `data/config/difficulty_score_model_v1.json`, `difficulty_score_model_v2.json`, `level_difficulty_analysis_v1.json`, `level_difficulty_analysis_v2.json`, `level_progression_v1.json`, `level_progression_v2.json`. No level data, catalog or gameplay change.
5. Boundary: no script under `scripts/` outside `scripts/difficulty/`, and no `.tscn`, references the frustration analyzer; it never touches `user://`, save or telemetry; profiles are never selected per player (no hidden DDA, CLAUDE.md 11.5).
6. New suite `tests/m36_frustration_v1.gd` (+ its `.uid` if the repo convention generates one) implementing the Acceptance criteria below with small fixtures and reduced seed counts so the whole suite is fast.
7. Docs: add a short "Implementation (SB-M36-015)" section to `docs/DIFFICULTY_FRUSTRATION_RISK_PROPOSAL_V1.md` (files, flags, status, runtime) and update `docs/09_DIFFICULTY_PROGRESSION_RETENTION_SYSTEM.md` section 7 plus `docs/11_LEVEL_DIFFICULTY_CALIBRATION_QA.md` section 7/8 pointer lines (F now computable, PROVISIONAL_SIMULATED_HUMAN, budget PROXY). ## Acceptance criteria
Let `GODOT=C:/Users/sekip/AppData/Local/Microsoft/WinGet/Packages/GodotEngine.GodotEngine_Microsoft.Winget.Source_8wekyb3d8bbwe/Godot_v4.7.2-stable_win64_console.exe` and `WT=C:/Users/sekip/Desktop/ScrubBots-factory/053-m36-015-frustration-build`. New suite `res://tests/m36_frustration_v1.gd` (must print `M36_FRUSTRATION_V1 PASS` on success and a `FAIL` line naming the failing check otherwise; tests below are numbered in the order of proposal section 5). Test fixtures: small corpus levels (e.g. `compact_hard_20`, `flow_stripes3_20`, `bottleneck_low_24`, `bottleneck_high_24`) and shipped L1 (20x20), with reduced runs (e.g. 4 per profile via the runs argument); no test may run a 10-level shipped sweep.
1. Determinism: same level/profile/seed twice gives an identical placement-column hash; a 1-level reduced run twice serializes to byte-identical JSON; two different run indexes diverge on at least one fixture.
2. Degenerate equivalence: with tau argmax, epsilon 0, mu 0, HUMAN_BR column sequence equals `run_policy(..., "ACCESS")` placements on L1 and 3 corpus fixtures.
3. Skill monotonicity: clearRate SKILLED >= CASUAL >= NOVICE on each tested fixture (ties allowed). If a fixture fails at the reduced seed count, report honestly with the observed rates; do not tune profiles to pass.
4. Discrimination, pairs declared before measuring: retryRisk(compact_hard_20) >= retryRisk(flow_stripes3_20) and retryRisk(bottleneck_high_24) >= retryRisk(bottleneck_low_24). A failing pair is recorded as a finding in the evidence and the suite then asserts only that the values are finite and reports them (do not change the pair or the profiles to force a pass).
5. Aggregator units on crafted run lists (no engine): late failure uses strictly > 0.70 (0.70 not late, 0.71 late); INCONCLUSIVE runs excluded from clearRate and counted; no LOST runs gives lateFailure 0 with LOST count 0; near-miss counts >= 0.90 (0.90 yes, 0.89 no); Wilson interval within 0..1 and contains the point estimate.

## Out of scope
- A required full 10-level `--frustration` run (about 5.6 h per the proposal). It is optional evidence: if the builder runs it (background, `--runs 8` or the config default), record real wall time and per-level numbers in the job evidence and TASKS.md, honestly labelled; skipping it is not a failure. Shipped L1..L10 are ad hoc and informational only, never calibration targets.
- Calibrating the profiles, changing F weights, score/analysis model versions, any existing config, level data or campaign data.
- Parallel workers, prefix caching, wiring F into CampaignBuilder, acceptance gates, Level Factory, runtime or UI.
- Timer, move limit, Heart/economy changes (Hearts-per-clear is a diagnostic only), per-player profile assignment or any use of saves/telemetry.

## Assumptions
- The run_policy `chooser` hook is the smallest reuse path; the v2 analyzer file is touched only for that default-off parameter, and its existing suites prove no behaviour change.
- Wilson interval and diagnostics follow the proposal formulas; `attemptSecondsProxy` = think-time sum plus route length / 6 cells/s, median over attempts, labelled PROXY.
- Reduced seed counts (2-4 per profile) are statistically weak, so tests 3 and 4 are reported honestly and a miss on a declared pair is a finding, not a build failure; test 3 uses ties-allowed comparisons and the builder may raise the per-fixture run count (still small fixtures) to avoid noise, without altering profiles.
- Suite file location follows the existing `tests/m36_*.gd` pattern; the user-supplied command form `-s res://tests/<suite>.gd` is used throughout.
