# Runtime / ProofKernel target parity (SB-CAMPAIGN-RUNTIME-KERNEL-DIVERGENCE)

> Feature: the shipping runtime chooses different targets than the ProofKernel (the solver that proves every release-pool level winnable). L22 is unwinnable by its intended clicks in the real runtime in all layouts; L18/L20 depend on layout/pacing. Suspected cause: kernel routes each slot from a fixed logical origin below the board ((slot+0.5)*w/cap, `_origin_for_slot`), while the runtime uses laid-out screen slot positions (`SlotOriginProvider`). If true, gameplay truth (WHAT target) depends on device layout. Preferred direction: runtime TARGET SELECTION uses the same canonical logical slot origins as the kernel, presentation keeps animating from on-screen slot positions. Also check pacing (runtime must not interleave dispatches in a way the kernel never models; decide queue/serialize vs model it; no new difficulty mechanics, CLAUDE.md §10). Acceptance: new suite replaying every production level's intended clicks (L1..L30) through the real runtime (bare host and app-root layout at 2+ viewport sizes) all WIN; per-click target equality with the kernel on L18, L20, L22; m55_long_session PASS (30 levels); m52_owner_supply_plans + campaign_l11_l30 still PASS; one CI validation_only run green.

## Context

Files (worktree-relative):
- Kernel: `scripts/gameplay/solver/proof_kernel.gd`. `_run_to_quiescence` runs WAVES: all eligible slots claim against the SAME pre-wave board (`claim_for_slot`, origin `_origin_for_slot` = `((slot+0.5)*w/cap, h+4)`), then ALL the wave's clears are applied, then the next wave (clears wake every WAITING lane). `apply_placement` places one batch then runs to quiescence. Its header already admits: "Runtime travel time may let later waves claim before earlier clears land, selecting different same-color cells ... SOLVED is a proof for this canonical timing only".
- Runtime: `scripts/gameplay/dispatch/auto_dispatch_scheduler.gd` (`begin_wave`, `queue_lane`, `step_lane`, `_attempt_slot`, `_on_authenticated_clear` -> `_wake`), driven by `scripts/gameplay/runtime/production_runtime_controller.gd` `tick()` (a new wave starts every cadence interval whenever the previous wave's lanes are serviced, regardless of bots still flying; `request_immediate_step` -> `queue_lane` fires a single lane on placement). Origins: `scripts/gameplay/runtime/slot_origin_provider.gd` (laid-out slot anchors mapped to board-local), bound in `production_gameplay_host.gd` ~line 317.
- WHAT/HOW: `scripts/gameplay/targeting/target_selector.gd` (order bottom-most, left-most, index; origin-independent) and `scripts/gameplay/dispatch/production_target_access.gd` (reachability via `RoutingSystem`; for an outside-board origin the prefilter uses perimeter/open-cell masks only, no dependence on the origin x).
- Existing evidence: `coordination/sessions/FACTORY/079-campaign-test-fix/build.md`; `tests/m55_long_session.gd` (`_drive` + `_quiet`, 30 levels, currently red at L18 in the app root); `tests/m52_owner_supply_plans.gd` (`_play_clicks`, L1..L10); `tests/campaign_l11_l30.gd` (kernel-only replay of L11..L30 plans); `tests/m52_r01_parallel_runtime.gd`, `tests/m52_r02_early_slot_release.gd`.

### Investigation result (done while writing this spec; the builder must re-confirm in Requirement 1)

The origin hypothesis is NOT supported. A scratch probe on the bare host, level 22, full-quiescence driver (click, tick until no live assignment, no moving bot, every occupied slot WAITING):
- default `SlotOriginProvider`: rejected (LOST) at plan click 27/43;
- scheduler `_origin_provider` swapped for the kernel's `((slot+0.5)*w/cap, h+4)` origins: STILL LOST, at click 25/43.
Swapping origins does not restore parity. Static reading agrees: selector order does not use the origin and reachability for outside starts is origin-independent. The remaining difference is TIMING: in the runtime, a later wave (cadence) or a placement lane (`queue_lane`) claims while earlier bots are still in flight, so their targets are still ACTIVE (blocking, reserved). The kernel instead claims each wave against a board where every previous wave's clears have landed. Same-color/other-slot picks then differ and the runtime can reach a dead end the kernel's trajectory never visits. This also explains the layout/pacing dependence (travel length and frame timing change who claims first). The kernel is not wrong: its dead-end and DEADLOCK soundness argument (quiescent = no future progress) holds, and claim semantics are identical.

So the origin-for-selection change in the request is not the fix, and the layout (`SlotOriginProvider`) is not shown to affect WHAT. Leave `SlotOriginProvider` and presentation as they are.

## Assumptions

- The origin is not the cause (measured above), so the "use kernel origins for selection" direction is dropped; keeping presentation origins is safe because reachability and selection are origin-independent for outside-board starts. Reason: a swap of origins in the probe left L22 LOST.
- The barrier lives in the scheduler/controller, not the kernel, because the kernel's claim semantics are right and the kernel doc already defines the canonical timing; making the runtime obey it keeps the existing proofs valid with no re-proof. A kernel that models continuous bot travel is rejected as unbounded and layout/speed dependent.
- Fast taps are not serialized: dispatch of the new batch waits for the barrier but input is accepted, to avoid inventing a tap-lock mechanic. A fast-tap sequence is a different click sequence than the kernel's; no equality is claimed for it.
- A slower dispatch start after a placement (waiting for in-flight bots) is accepted as the price of correctness; if the measured slowdown is large the owner is asked through one TASKS.md line, work continues.
- The unlisted L1 (greedy, no plan) is only required to WIN.
- Viewport sizes for `app_root` are builder's choice as long as there are at least two with different aspect or scale.
