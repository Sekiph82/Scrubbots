## Context

- Today's "winnable" proof is `scripts/gameplay/solver/proof_kernel.gd`. It settles each placement's dispatch cascade fully before the next placement (waves of claims against a pre-wave board, all clears land before the next wave). The shipping runtime does not: `scripts/gameplay/runtime/production_runtime_controller.gd::tick(delta)` advances bots by `delta*factor`, starts a cadence wave every `GameplaySpeedAuthority.cadence_interval()` (1/3 s at 1x) while bots still fly, services `MAX_LANES_PER_FRAME = 1` lane per frame, and a placement queues its own lane (`request_immediate_step -> scheduler.queue_lane`). Later waves therefore claim while earlier targets are still ACTIVE, picks differ from the kernel, and the owner's intended clicks can dead-end: L22 (`data/levels/supply/level_022_crab_supply_v1.json`) is unwinnable, L18/L20 depend on pacing (079 evidence: `coordination/sessions/FACTORY/079-campaign-test-fix/build.md`; TASKS.md row `SB-CAMPAIGN-RUNTIME-KERNEL-DIVERGENCE`). Swapping slot origins was measured NOT to fix it (it is timing, not origin).
- Runtime assembly to reuse: `scripts/gameplay/runtime/production_gameplay_host.gd` (`build()`, `get_runtime()`, `get_input_controller().activate_front(col)`, `get_slots()` with `rightmost_empty_index()` / `is_occupied` / `get_remaining`, `get_scheduler()` with `live_assignment_count()` / `is_slot_waiting`, `get_agent_layer()`, `get_completion().is_won()/is_terminal()`, `get_board()`, `get_supply()`). Existing headless driving pattern: `tests/m52_owner_supply_plans.gd::_runtime/_play_clicks` (AppState frontier -> host, `runtime.set_process(false)`, `runtime.tick(dt)`), and `tests/m55_long_session.gd::_drive/_quiet` (app root `scenes/app/main.tscn`).
- Plan format: `data/levels/supply/<id>_supply_v1.json` (`intendedColumnClicks` 1-based column per click; `columns` are immutable Studio supply). Loader: `scripts/gameplay/supply/supply_plan_loader.gd` (`load_plan`, `load_engine`).
- Release-pool acceptance today (item 4 of the request): `tools/import_release_pool_levels.py` line ~74 only asserts the Studio's own `solver_status == SOLVED and replay == WIN` and copies it to metadata `releasePool.studioSolverStatus/studioReplay`; `tests/campaign_l11_l30.gd::_win` replays the plans through the ProofKernel only. The Studio tool itself lives OUTSIDE the repo (`STUDIO` path in the importer). Nothing in-repo replays plans through the real runtime except m52 (L2..L10) and m55.
- Determinism facts the builder must confirm (Requirement 1): runtime tick is a pure function of (state, dt) (no `randf`, no wall clock in the dispatch/travel path), so a fixed `dt` is deterministic. It is NOT frame-rate independent: lane service is one lane per frame, cadence accumulates per frame, bot travel advances in `speed*dt` steps and arrives on a frame boundary, `_accum` drops backlog above one interval. So device FPS (30/60/120) can change which claim happens first. Existing tests use `dt = 1.0`, which is far coarser than any device and is NOT a valid timing model for this job.

3. New file `scripts/gameplay/solver/real_play_driver.gd` (RefCounted, preload by path, no `class_name`; reuse the real host, never reimplement the runtime). API (names indicative): `play_on_host(host, clicks, dt, max_frames) -> Dictionary` and `play_level(parent_node, entry_id, clicks, dt) -> Dictionary` (builds the host from an AppState frontier like `m52._runtime`, frees it). Human policy, exact:
   - Before every `tick(dt)` (including frame 0): while a slot is free (`slots.rightmost_empty_index() != -1`) and a click remains, call `input.activate_front(col)` with the next column. So the 5 slots are filled at frame 0 and any slot that frees (batch fully dispatched while other bots still fly) is refilled on the next frame boundary. Never wait for quiescence, never wait for bots to land.
   - Result: `won`, `frames`, `clicks_placed`, `rejected` (first rejected click with reason; a rejection on a legal column with a free slot is a driver bug and fails loudly), `cleared_sequence` (ordered cell indices, via `host.get_clearing_loop()`/the clear event or a board diff per frame) for determinism checks, `final` state (ACTIVE count, supply exhausted, slots empty), and `stuck` (quiescent dead end: no live assignment, no moving bot, every occupied slot WAITING, ACTIVE > 0, and no further click possible or all slots full).
   - Levels without a plan (L1, M23 generator) use the same policy with "first column whose `activate_front` succeeds" as the choice.
4. Real-play search in the same file (`search(...)`): the only decision is WHICH supply column to pick each time the policy needs a click. Bounded, deterministic DFS with backtracking over column choices (a beam is acceptable if the builder shows DFS too slow):
   - Branch order: the level's current `intendedColumnClicks[depth]` first while the prefix still equals the plan prefix, then remaining legal columns ascending. So the search reproduces the current plan until it fails and then backtracks from the failure.
   - Each node is evaluated by replaying the prefix from a fresh host under the human policy (deterministic replay; no runtime snapshotting). A node ends WON, `stuck` (prune), or reaches the next decision point (branch).
   - Bound by a node budget constant (not wall clock, so results are reproducible); a winning leaf is accepted only after it also wins at the other sensitivity dts (Requirement 2); otherwise the search continues.
   - Returns `SOLVED` (with clicks), `UNWINNABLE_WITHIN_BUDGET` or `EXHAUSTED` (full search space explored, no win = proven unwinnable for every column order under the model). Distinguish these (CLAUDE.md §18 UNSOLVABLE vs INCONCLUSIVE).

## Assumptions

- "Free slot" means `slots.rightmost_empty_index() != -1`, i.e. the M52-R02 early release (last waiting Scrubby departed) counts; this is what a human sees and what the owner described.
- Several clicks may land in the same frame while several slots are free (frame 0 fills all five). Clicks are applied in plan order before the frame's tick.
- Canonical dt is 1/60 because it is the dominant mobile frame time and the production target; 1/30 and 1/120 bound the realistic range. `dt = 1.0` used by older tests is discarded for plan proof.
- A plan is "failing" if it is not WON at any of the three dts; this is stricter than 1/60 alone and keeps regenerated plans robust across devices.
- Prefix-replay DFS is chosen over runtime snapshotting because the runtime is deterministic and levels have at most ~120 clicks; the node budget and search stats are recorded so the builder can tune the constant.
- The importer shells out to Godot (env `GODOT`) because the verifier must run the real runtime; a missing Godot is a hard error so the gate cannot be silently skipped.
- Provenance lives in a separate file because the supply plan schema (and its fail-closed loader) belongs to the Studio content contract.
