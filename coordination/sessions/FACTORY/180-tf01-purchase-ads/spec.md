# SB-TF-01: fix StoreKit/Play purchases and make ads fill on TestFlight/internal builds

> Feature: Owner TestFlight feedback 2026-11-18 (iPhone, build 0.1.0 (24), release build with billing_ads): (5) a purchase tap shows "The purchase didn't go through"; (6) ads never show (rewarded videos "do not work"). Audit the full StoreKit and Play Billing flows, fix concrete bugs, surface the real error code/message in logs and failure text for debug/TestFlight builds. Internal/TestFlight builds use Google's official test ad unit ids so ads fill; real ids only for an explicit public release. When a rewarded ad is unavailable or fails, the player sees a short native message (EN+TR). Verify AdMob init, consent/UMP and load-retry. No secrets in the repo, no public store release.

## Context
- StoreKit: `scripts/economy/app_store_provider.gd` wraps the godot-ios-plugins "inappstore" singleton `InAppStore` (pinned commit built in `.github/workflows/ios-ipa.yml`, step "AdMob + InAppStore iOS plugins"). `_on_event` maps `purchase` events: `ok` -> purchased, `error` -> `failed` (the plugin's error text/code in the event is DROPPED), `progress`+type_code 4 -> pending. `query_products` sends `{"product_ids": ...}` and only reads `ids`/`localized_prices` of `product_info`; `invalid_ids` and `result != ok` are ignored silently (so an id mismatch leaves no price, or a purchase of an unloaded product errors with no trace).
- Play Billing: `scripts/economy/play_billing_store_provider.gd` (same contract, GodotGooglePlayBilling 3.3.0), covered by `tests/m57_native_providers.gd`.
- `scripts/economy/store_service.gd`: `purchase()`, `deliver()` (outcome other than "purchased" -> `{ok:false, reason:outcome}`), `resolved` signal. Product ids come from `data/config/store_products_v1.json` (`scrubbucks_100/550/1200/2600/7000`, `no_ads`).
- UI failure text: `scripts/ui/shop/shop_screen.gd` `_feedback`/`_on_store_resolved` use `UiText.t("SHOP_STORE_FAILED")` ("The purchase didn't go through.", TR in `scripts/ui/ui_text_tr.gd`) with no reason detail.
- Ads: `scripts/economy/admob_ad_provider.gd` over plugin node `res://addons/AdmobPlugin/Admob.gd`, installed in `scripts/app/main.gd::_install_native_providers`. Flow: UMP consent -> iOS ATT -> `initialize` -> load interstitial + rewarded. `rewarded_ad_failed_to_load` / `interstitial_ad_failed_to_load` just set `"none"` (no log, no error code, retry only on the next `is_available()` call). Real ids are used whenever `addons/AdmobPlugin/scrubbots_real_ids.gd` exists; the workflows (`ios-ipa.yml` ~l.268-282, `android-family-first10.yml` ~l.712-740) write it and set `is_real=true` and the real `app_id` for EVERY `build_type=release` build, which includes TestFlight uploads. A new unpublished app gets no/low fill with real ids, hence "ads never show".
- Rewarded UI: `scripts/ui/daily/rewarded_ads_screen.gd::_reason_text` already maps `unavailable`/`provider_refused` to `REWARDED_UNAVAILABLE_NOTE`; the builder must verify that every Rewarded-ad entry point (Rewarded Ads screen, heart refill, failure assistance, any other `rewarded.request`/`start_rewarded_*` caller; grep them) shows a visible message when the ad is unavailable, fails to load, or fails to show, and shows nothing silently.
- Docs: `AGENTS.md` (ads/store paragraph, l.~31), `docs/RELEASE_BUILDS.md` (l.~105), `docs/PRIVACY_DATA_INVENTORY.md` (l.34, "Google TEST ad units until the owner's ids are set").

## Requirements
1. Audit the whole StoreKit path (plugin API names/args against the pinned plugin source in the CI step, product request, event shapes, purchase, `finish_transaction`, `restore`, error mapping) and the Play Billing path. Record findings in `factory/jobs/180-tf01-purchase-ads/build.md` as concrete cause list: for each suspect (id mismatch incl. bundle prefix, purchase before products loaded, wrong event keys/signals, missing finish, `refresh_prices()` never called or called before the singleton is ready, invalid ids ignored) say confirmed bug / ruled out with the code line. Fix every confirmed bug.
2. Providers keep the real error: `AppStoreProvider` (and `PlayBillingStoreProvider`) pass the store's error text/code through `deliver` as an extra field (e.g. `"error": "<code>: <message>"`) and `StoreService.deliver` returns it in the result (`out["error"]`) and `resolved`. Also `push_warning`/`print` a single log line `STORE_ERROR product=<id> code=<..> msg=<..>` for every failed purchase, failed product query and every non-empty `invalid_ids` (`STORE_INVALID_IDS ...`). No behaviour change for success/cancel/pending/duplicate.
3. The shop failure feedback appends the error detail in debug builds and in builds with the `billing_ads` plugin (TestFlight), via a UiText key with `%s` (EN + TR), e.g. "The purchase didn't go through. (%s)". Plain cancel stays silent as today. The detail is never shown if empty.
4. If the audit finds products are not loaded when the Shop opens, trigger `refresh_prices()` when the Shop opens and after the provider is installed (once), and retry once if the first `product_info` returns an error. Do not add polling loops.
5. Ad id switch: a build-time "ads test mode". Add workflow input `ads_test_mode` (boolean, default `true`) to `ios-ipa.yml` and `android-family-first10.yml`. When true (any build_type) the workflow does NOT write `scrubbots_real_ids.gd`, uses Google's official sample app id (iOS `ca-app-pub-3940256099942544~1458002511`; Android sample id already used by the debug path) and `is_real=false`, so Google test units are requested (`admob_ad_provider.gd` already keeps test units when the ids file is absent). Real ids and the secrets-missing hard failure apply only when `ads_test_mode == false` AND `build_type == release`. `ads_test_mode=false` with `build_type=debug` is rejected with a clear `::error::`. The existing `billing_ads app check` step must print the resulting mode (`ads_mode=test|real`) and fail if test mode produced a real id file. No secret value is ever echoed.
6. `AdmobAdProvider` load-retry and diagnostics: log (`ADS_LOAD_FAILED kind=<rewarded|interstitial> code=<..> msg=<..>`) every failed load using the error argument the signal already carries; after a failed rewarded or interstitial load schedule ONE bounded retry with backoff (e.g. 5 s, then 15 s, then 45 s, cap 3 consecutive automatic retries, counter reset on a successful load) using an injected/testable timer, not a busy loop. `is_available()` must keep returning false while not ready. Log `ADS_INIT_DONE` after SDK init and log consent/ATT failure paths (they must still fall through to init, as today).
7. Player message: whenever the player asks for a rewarded video and it cannot play (not ready, load failed, show failed), a short native text is shown instead of nothing: reuse `REWARDED_UNAVAILABLE_NOTE` for "not available", and for a failed show/`failed` outcome the existing `REWARDED_NO_GRANT`/`REWARDED_REASON_FAILED`. Every caller path found in the audit that currently shows nothing gets the message. EN and TR strings exist in `ui_text.gd` and `ui_text_tr.gd` for any new key; the existing UiText EN/TR parity test must stay green.
8. Tests (headless, fake backends, no SDK/network): extend `tests/m57_native_providers.gd` (keep the exact-case-guard style; bump the expected case list and the final PASS line, and update the matching grep in `android-family-first10.yml` l.~445 area and any other place that greps the old `9/9` line) with cases covering: StoreKit `error` event carries code/message through `StoreService.resolved`; `invalid_ids` / `product_info` error produce a logged/recorded diagnostic and no price; purchase failure leaves product purchasable again (`_pending` cleared); rewarded load failure schedules a bounded retry (max 3, reset on success); rewarded unavailable yields the UI reason text. Add a small test (new suite or inside `m57_native_providers`) for the ads-mode switch: with `real_ids` path absent `is_real` is never set, with a fake ids file it is set. Workflow YAML must pass a parse check (`python -c "import yaml,sys; yaml.safe_load(open(f))"` or `actionlint` if present).
9. Docs: update `AGENTS.md` ads/store paragraph, `docs/RELEASE_BUILDS.md` (new `ads_test_mode` input, TestFlight/internal = test units, real ids only for explicit public release with `ads_test_mode=false`; how to read `STORE_ERROR` in the device log), `docs/PRIVACY_DATA_INVENTORY.md` wording that matches. Update the SB-TF-01 entry in `TASKS.md` with evidence only after review (factory loop does that).
10. `build.md` has an "Owner device checks" section listing what only a device can prove (not faked): sandbox tester signed in on the iPhone; Paid Apps Agreement active in App Store Connect; the six product ids exactly match App Store Connect (state READY_TO_SUBMIT is fine for TestFlight sandbox); a purchase shows the sandbox sheet and grants once; rewarded test video plays and grants; the error detail text if a purchase still fails.

## Assumptions
- "Test mode" is chosen at build time via workflow input defaulting to true (simplest clean switch; runtime already falls back to Google test units when the ids file is absent).
- Detail text in the failure message is shown in debug and `billing_ads` builds only (TestFlight diagnosis); a public release can drop it by the same flag later without a new mechanism. If the builder finds no cheap way to tell, showing it always is acceptable.
- The inappstore plugin's error fields are not known from this repo; the builder reads the pinned source (commit in `ios-ipa.yml`) to name the real event keys and records them in `build.md`.
- Retry cap of 3 with 5/15/45 s backoff is a conservative default; ads then re-load lazily on the next player request via `is_available()` as today.
