## Requirements
1. Add ONE thin runner `tools/difficulty_playtest.gd` (SceneTree script, headless). It reuses `Tool.reference_inputs`, `Analyzer.measure/score`, `DifficultyProgressionV1` and `SolvabilitySolver`; it adds no scoring logic. For each catalog entry (read via `LevelCatalog`, not a hardcoded list) it does a FRESH run: solver status, visited count, wall ms; measure with the oracle trace; score D and vector; and replay counts (steps/decisions, total clears = dispatches, dispatch waves, route failures). Fresh run takes at most a few minutes total; if a level's fresh measure is too slow the runner may fall back to the committed raw record for measure only and must label that per level (`source: fresh|committed_raw`).
2. Runner writes `coordination/sessions/FACTORY/044-m36-005-difficulty-playtest/playtest_v1.json` with per level: order, id, w x h, class (from cadence), slot, challengeScore D, vector W/C/A/U/B/R/S, targetChallenge (11.2), signedDelta, acceptanceWindow, sessionLoad value, frustrationRisk (status and scalar as produced, null stays null), solver status, visited, solver ms, dispatches, decisions, dispatchWaves, routeFailures, measure ms; plus top-level model/provenance versions, recovery guards (boss->recovery drops, actual vs designMinimumDrop), and an `anomalies` array (see 4).
3. Anomaly rules, mechanical and computed by the runner: (a) CADENCE: class of order n differs from 11.1 slot table; (b) LANE_MISS: acceptanceWindow is not in-window (report SOFT vs OUT_OF_HARD_LIMIT separately, using `challengeTolerance` from level_progression_v1.json); (c) RECOVERY: a recovery guard in `recovery_guards()` fails; (d) SOLVER: status not SOLVED; (e) ROUTE: routeFailures > 0 or solved=false or finalActive > 0; (f) LONG_HIGH_FRICTION: two consecutive levels both with Session Load and Challenge D above the pack median (or the repo's own threshold if config defines one; cite it); (g) BOUNDARY: any order whose class differs from the cadence-derived class in `level_progression_v1.json`.
4. Write `docs/DIFFICULTY_PLAYTEST_2026-10.md`: method, tool and model versions (provenance), one table with the per-level columns from req 2, an anomaly section grouped by rule with level ids and numbers, a "what this does and does not prove" paragraph (simulated oracle path, Frustration provisional, no human feedback, owner gate given by 0D.1), and the list of filed follow-up task IDs. Numbers in the doc must be generated from or equal to the JSON (runner may emit the table; builder pastes it).
5. TASKS.md: (a) tick `SB-M36-005` (`- [x]`) with a short evidence note (commit, doc path, JSON path, LOCAL_PASS suites, label `CLAUDE_PEER_REVIEW` only if a reviewer did it), and replace the stale OWNER_REQUIRED note; mark its READY queue row DONE. Each item must say what to do and that it must not change coefficients/model version without a new model version (11.3); calibration or level changes are proposals, not done here. If a rule yields no anomaly, file nothing for it.
6. ## Assumptions
- The shipped catalog is 10 levels, so 11.2 progression P(k) is 0 for all (k=0); decay of lane targets over campaign age cannot be tested here beyond the existing unit tests (reason: no shipped level past order 10).
- "Local play" = automated oracle-trace replay through the production routing/kernel (the existing measure path), because the owner gate is given and no bot-driver beyond that exists for difficulty scoring.
- Lane-target tolerance uses the repo's `challengeTolerance` from `level_progression_v1.json` (reason: already versioned, avoids an invented tolerance).
- Existing M53 evidence already finds all 10 levels outside the default window; the likely outcome is a small number of grouped follow-up items rather than one per level (reason: job-sized, non-duplicate). Builder groups by cause and may cite level lists.
- Task IDs for new items continue the SB-M36-0xx numbering after the highest existing SB-M36 ID found by grep (reason: avoids collisions).
- Anomaly rule (f) uses the pack median as threshold unless a config threshold exists (reason: conservative default, cited in the doc).
