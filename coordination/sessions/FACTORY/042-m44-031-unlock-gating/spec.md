# Feature unlock gate (SB-M44-031 part 1): data table, Home + booster locking, grandfather rule

> Feature: SB-M44-031 re-sequence FTUE to the 2026-10-22 owner unlock table. Data-driven unlock gate (one config table keyed by feature -> campaign level, SB-M44-011) that locks Home entries and booster buttons until the frontier level reaches the table level; existing saves are never re-locked. This job is PART 1 of a split: gate table + Home/booster locking + grandfather + the minimum FTUE tweaks so no coachmark points at a locked control. Part 2 (lesson re-sequencing per booster, starter grant deferral, welcome-task deferral, retiring soft_no_hard_locks wording in docs) stays in TASKS.md SB-M44-031.

## Context
- Owner unlock table (TASKS.md SB-M44-010, `coordination/OWNER_META_PROGRESSION_DESIGN_V01.md`): Hearts L1, Gift Bar L1, Daily 4, Shop 8, Tasks 12, Collection 20, Card Packs 20, Robots 25, Events 30, Achievements screen 35 (stats from L1), RANKS 40; boosters +1 Slot 6, Random 11, Selector 16, Tornado 21.
- Frontier: `AppState.progression.current_level()` (`scripts/progression/level_progression_service.gd`; `record_win(n)` advances it). FTUE new-profile flag: `economy.ftue.is_new_profile()` (set by `AppState.bootstrap_new_profile`, `scripts/app/app_state.gd` ~L224-260; only fresh saves get it).
- Today nothing is locked: `data/config/ftue_onboarding_v1.json` has `feature_discovery.policy = soft_no_hard_locks` with `available_from_first_home`, validated by `scripts/app/ftue_config.gd` (rejects anything but that policy).
- Home (`scripts/ui/home/home_screen.gd`): shortcuts `LEFT_SHORTCUTS` (shop, collection), `RIGHT_SHORTCUTS` (tasks, daily), `LIVE_SHORTCUTS`; enable logic at ~L1304 (`Shortcut_<id>.disabled = ...`); bottom nav built in `_build_bottom_nav` (~L1092: events, robots, home, leaderboard=RANKS, settings; `Nav_<id>`). Gift Bar is its own control, not a shortcut button. `main.gd` supplies `set_app_shortcuts`.
- Booster bar: `scripts/ui/gameplay_screen.gd` already has `BOOSTER_LOCKED` ("locked": disabled + overlay, price hidden) but nothing produces it. States come from `ProductionGameplayHost.booster_states()` (`scripts/gameplay/runtime/production_gameplay_host.gd` ~L899), whose doc comment says "No feature-unlock authority exists for boosters yet".
- FTUE director `scripts/app/ftue_director.gd` picks steps from `ftue_onboarding_v1.json` lessons (L1 Home steps `home_daily`, `home_tasks`, `home_play` guarded by `when`; L2 lesson `l2_boosters` with `boosters` lists).
- Tests that touch this: `tests/m44_ftue.gd`, `tests/m42_home*.gd`, `tests/m28_c002_c001_gameplay_v02.gd`, `tests/m39c_boosters.gd`, `tests/m43_c003_c001_acquisition.gd`, `tests/m42_navigation.gd`, `tests/m46_rm003_ftue_coach_performance.gd`.

## Requirements
1. New versioned config `data/config/feature_unlocks_v1.json` (schema string, version, one `unlocks` map feature id -> integer unlock level >= 1) with exactly the table above. Feature ids: `hearts, gift_bar, daily, shop, tasks, collection, card_packs, robots, events, achievements, ranks, plus_one_slot, random, selector, tornado` (booster ids must equal `BoosterInventory.BOOSTERS` ids). No level number may appear in UI code.
2. New strict reader `scripts/progression/feature_unlocks.gd` (RefCounted, same fail-closed style as `ftue_config.gd`): `load_config`, and `is_unlocked(feature_id, frontier_level, grandfathered: bool) -> bool`, `unlock_level(feature_id) -> int`. Unlocked iff `grandfathered or frontier >= unlock_level`. Unknown feature id -> unlocked (never lock something not in the table). Malformed/missing config -> everything unlocked (fail open, since a broken file must not strand a player behind locks) with `ok:false`.
3. Grandfather rule (ORCHESTRATOR DEFAULT, owner can override): a save is grandfathered when it is NOT a new FTUE profile (`not economy.ftue.is_new_profile()`), i.e. every pre-existing/migrated/established save keeps all features. Fresh profiles are gated purely by frontier. A feature once reached stays unlocked because the frontier never decreases. `AppState` exposes one helper (e.g. `feature_unlocked(id) -> bool`) combining the reader, `progression.current_level()` and the grandfather flag; all UI asks only this.
4. Home gating: shortcuts shop, collection, tasks, daily and nav tabs robots, events, leaderboard(RANKS) are disabled while locked (reuse existing disabled styling), with a tooltip/label showing the unlock level via a new localized string key (e.g. "Unlocks at level N") taken from the table. Badges for a locked entry are hidden/0. Gift Bar and Hearts are never gated (L1). Already-unlocked entries behave exactly as today. Locked entries must not emit `shortcut_requested`/`nav_requested`-driven navigation.
5. Booster gating: `booster_states()` returns state `"locked"` for a booster whose feature is locked (takes precedence over available/purchasable/unavailable, so a charge held from the starter grant is shown locked, not lost or spent). Locked booster press does nothing. Charges are never removed or altered by locking.
6. Coachmarks never target a locked control: the FTUE director skips a Home step whose `target` is `shortcut:daily`/`shortcut:tasks` while that feature is locked, and drops locked boosters from a `boosters` step list (a step with no remaining boosters is skipped). Skipping must not mark steps seen and must not break the L1-L3 window closing (`home_play` and the L1/L3 lessons still run). No new lesson copy, no new step content.
7. `soft_no_hard_locks` is replaced in `feature_discovery` handling: `ftue_config.gd` must no longer require that policy string; the `feature_discovery` block in `ftue_onboarding_v1.json` is removed or reduced to a note pointing at `feature_unlocks_v1.json`; `available_from_first_home` is no longer read by gating logic.
8. Not in this part (do NOT change): starter booster grant (`bootstrap_new_profile`, 2 charges each stay granted at L1 and stay in inventory), the 100 SB welcome task install, lesson levels/ids, reward amounts, Gift Bar rewards, pending-pack inventory (SB-M44-025).
9. Docs: update AGENTS.md (new config + reader + `AppState.feature_unlocked` entry point, the grandfather default), `docs/16_FTUE_FEATURE_UNLOCK_AND_RETENTION_SURFACES.md` (hard unlock gating now in force per the owner table; note part 2 pending), `scripts/progression/README.md`, and the stale comment on `booster_states()`. In TASKS.md mark SB-M44-010/011 evidence and split SB-M44-031 into done part 1 and a new READY part 2 line listing: per-booster lessons at 6/11/16/21 reusing existing lesson copy, move Daily/Tasks coach marks to first Home after L4/L12, defer starter grant and 100 SB welcome task until their feature unlocks (kept pending, never deleted), plus resolving the interim state below.

## Assumptions
- Split into part 1/2: lessons, grants and welcome task need new ordering logic and persistence for deferred state; together with the gate they exceed one job.
- Interim state after part 1 (documented in TASKS.md part 2): a fresh profile holds 8 starter charges and a welcome task it cannot use until the matching feature unlocks; nothing is lost, and Tasks (L12) hides the welcome task meanwhile. Accepted as a safe intermediate because part 2 follows next.
- Grandfather = "not a new FTUE profile" is the cheapest rule that never re-locks existing saves; a profile created by a pre-update dev build and still flagged new at low frontier would be gated. Orchestrator default; owner can override.
- Fail open on bad config / unknown id, opposite of FTUE config's fail-closed, because a locked-out player is worse than an unlocked feature.
- Gating shop on Home at L8 does not block the in-gameplay booster purchase popups (they stay as today; locked boosters are not purchasable anyway).
- Hearts and Gift Bar rows exist in the table for completeness (L1) but have no UI to gate.
