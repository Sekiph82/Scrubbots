# SB-M34-005 — Prevent vibration spam

Status: IMPLEMENTED
Requirement: deterministic throttle/debounce/coalesce or equivalently bounded
policy. Cleaning bursts must not produce unbounded vibration requests. Expose
request/played/suppressed diagnostics for tests. 1x/2x must not change gameplay
truth.

## Production owner
`HapticsController.request_cleaning()`:
- constant `CLEAN_THROTTLE_MS = 60` window.
- Rejected requests count into `suppressed_clean`.
- Diagnostics via `get_diagnostics(Category.CLEANING)`.

## Direct tests
Burst of 20 cleaning requests in one tick:
- played <= 2 within the throttle window;
- platform call count == played;
- suppressed == 40 - played across two bursts (OFF + throttle).

Gameplay effect: haptics never blocks the M20/M30 clear transaction. 1x/2x
changes event density but not the throttle law (played is capped by wall-clock
window, not gameplay delta). Explicit assertion: platform_calls_count == played
in both bursts.

## Expected / failure
Expected: bounded played per real-time window. Failure: unbounded played, or
gameplay clear observed to be delayed by a vibration request.

## Actual
PASS.
